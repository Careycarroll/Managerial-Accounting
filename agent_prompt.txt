## 1. Project Summary

A Vite-based multi-page web app that teaches Horngren's Cost Accounting (17th Edition) through interactive tools. Three sections:

- **Learn** — 24 chapter pages with interactive calculators, show-work panels, key terms
- **Practice** — 25 randomized multi-step calculation problems across 5 chapters, engine v3 with scenario + choice step support
- **Apply** — 12 business decision scenarios with three depth levels (Concept / Analysis / Simulation)

**Repo:** `~/Github Projects/Managerial-Accounting/`
**Live:** https://careycarroll.github.io/Managerial-Accounting/ (auto-deployed via GitHub Actions on push to `main`)
**Stack:** Vite 7, vanilla JS (ES modules), CSS custom properties, KaTeX, vite-plugin-pwa
**No frameworks. No build steps in source. All JS uses native ES modules.**

## 2. Critical Rules — Read Before Any Edit

### 2.1 Internal Link Rule (Highest-Leverage Failure Mode)

The site deploys under the subpath `/Managerial-Accounting/`. Bare absolute paths break navigation.

**HTML files — use `%BASE_URL%`:**

    <!-- CORRECT -->
    <a href="%BASE_URL%pages/learn/ch01.html">Ch. 1</a>

    <!-- WRONG — 404s in production -->
    <a href="/pages/learn/ch01.html">Ch. 1</a>

**JS files that render `<a href>` — use `import.meta.env.BASE_URL`:**

    // CORRECT — top-of-file constant
    const BASE = import.meta.env.BASE_URL;
    container.innerHTML = `<a href="${BASE}pages/learn/ch01.html">Ch. 1</a>`;

    // CORRECT — inline concatenation (when top-level const is awkward)
    const html = '<a href="' + import.meta.env.BASE_URL + 'pages/learn/ch01.html">Ch. 1</a>';

    // WRONG
    container.innerHTML = `<a href="/pages/learn/ch01.html">Ch. 1</a>`;

**Exception — these are auto-rewritten by Vite, leave alone:**

    <link rel="stylesheet" href="/css/base.css">      <!-- Vite handles -->
    <script type="module" src="/js/core/main.js">     <!-- Vite handles -->

**Substring matching in JS — leave hardcoded:**

    // In header.js — these are matchers against window.location.pathname, not links
    const isLearn = path.includes("/pages/learn");    // CORRECT — never change

**Audit command before commit (must return empty for JS links):**

    grep -rn '"/pages/' --include="*.js" js/ | grep -v 'path.includes'

### 2.2 Dark Mode Rule

Never hardcode hex colors in JS-rendered HTML. Always use CSS custom property tokens.

    // WRONG
    container.innerHTML = `<div style="background:#f0fdf4;color:#166534;">...</div>`;

    // CORRECT
    container.innerHTML = `<div style="background:var(--color-success-bg);color:var(--color-success);">...</div>`;

Token reference for JS output:

| Token | Light Mode | Dark Mode (auto via `data-theme="dark"`) |
| --- | --- | --- |
| `--color-success-bg` | light green | dark green |
| `--color-danger-bg` | light red | dark red |
| `--color-warning-bg` | light amber | dark amber |
| `--color-info-bg` | light navy | dark navy |
| `--color-poor-bg` | very light red | deep dark red |
| `--color-success` | green text | teal text |
| `--color-danger` | red text | red text |
| `--color-warning` | amber text | amber text |
| `--color-info` | blue text | light blue text |
| `--color-poor` | dark red text | bright red text |
| `--color-primary-text` | navy | light blue |
| `--color-accent` | gold | gold |

All custom properties defined in `css/base.css`. Dark overrides in `css/settings-panel.css`.

### 2.3 CSS Authoring Rule

Never write CSS inside Python triple-quoted strings passed through a shell heredoc. CSS in heredocs corrupts during shell expansion.

Always write CSS as a Python list of strings joined with newline:

    css_lines = [
        ".my-class {",
        "  color: var(--color-primary-text);",
        "  background: var(--color-card-bg);",
        "}",
    ]
    with open("css/file.css", "w") as f:
        f.write("\n".join(css_lines))

Always pipe discovery output to `audit.txt`. Never let it dump to terminal.

For multi-step discovery, group with braces:

    {
      echo "===== Step 1: ====="
      command1
      echo ""

## 3. Deployment

### 3.1 How It Works

`.github/workflows/deploy.yml` triggers on push to `main`. Two jobs:

1. **build** — checkout, `npm ci`, `vite build`, copy `dist/index.html` → `dist/404.html`, upload `dist/` as Pages artifact
2. **deploy** — publish artifact to `github-pages` environment

End-to-end deploy time: 60–120 seconds.

### 3.2 Deploy a Change

    git add -A
    git commit -m "feat: Section — Description"
    git push origin main

Watch the run at: https://github.com/Careycarroll/Managerial-Accounting/actions

After deploy succeeds, **hard-refresh** the live site (Cmd+Shift+R) or test in an incognito window. The PWA service worker caches aggressively.

### 3.3 Failure Modes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Deploy job fails "Resource not accessible by integration" | Pages source not set to "GitHub Actions" | Repo Settings → Pages → Source → GitHub Actions |
| Build job fails on `npm ci` | package-lock drift | Run `npm install` locally, commit lock file |
| Site loads but assets 404 | Wrong base path in `vite.config.js` | Confirm `command === 'build'` pattern (see §4.2) |
| Site loads but internal nav links 404 | Hardcoded `/pages/...` in HTML or JS | Apply rule §2.1 |
| Site shows old content after deploy | PWA service worker cache | Hard-refresh or incognito window |

### 3.4 Do Not Use

- `npm run deploy` — deprecated; the `gh-pages` package approach is obsolete
- Manual `gh-pages` branch pushes — Pages source is set to "GitHub Actions", not branch

### 4.3 Page Boilerplate

Every HTML page must include this inline script in `<head>` BEFORE any stylesheet links — it prevents flash-of-unstyled-content on theme/width preferences:

        var w = localStorage.getItem('pref-width');
        var f = localStorage.getItem('pref-font');
        var t = localStorage.getItem('pref-theme');
        if (w) r.style.setProperty('--max-width-tool', w + 'px');
        if (f) r.style.setProperty('--font-scale', f);
        if (t === 'dark') r.setAttribute('data-theme', 'dark');

## 5. Apply Section — Built

All 12 scenarios are complete at Concept + Analysis depth. One scenario (breakeven) has Simulation built.

### 5.1 Apply Page Pattern

Each Apply HTML page contains:

- Hero section with title, chapter badges, depth toggle buttons
- Three `<div class="depth-panel">` elements — only `.depth-panel--active` is visible
- For scenarios with Simulation: `depth-simulation-wrapper > depth-simulation-container`

### 5.2 Simulation Engine

`js/engine/scenario-engine.js` is a domain-agnostic state machine. All accounting logic lives in `js/engine/scenarios/*.js`.

**Engine features:**

- Three answer types per stage: `single-choice` (bell curve), `multiple-choice` (select all), `numeric` (free entry, tolerance-graded)
- Answer type randomly selected per stage per round
- Four score levels: optimal (1.0), acceptable (0.6), suboptimal (0.2), poor (0.0)
- `renderShowWork()` called after every decision
- Selection breakdown for multiple-choice with per-option correct/incorrect reasons
- Weight-based debrief rating
- `randomizeMetrics()` called on every init/reset
- Bell-curve option generator — optimal answer shifts position each round, irregular spacing
- Branching via `nextStage` string OR function

### 5.3 Scenario Definition Schema

    export const myScenario = {
      id: 'my-sim',
      title: 'Scenario Title',
      randomizeMetrics() { return { /* metrics object */ }; },
      metricDisplay: [{ key, label, format, poorIf? }],
      stages: [ /* see §5.4 */ ],
      reviewChapters: [{ label, href: import.meta.env.BASE_URL + 'pages/learn/chXX.html' }],
    };

### 5.4 Stage Definition Schema

    {
      id: 'stage-id',
      title: 'Stage N — Title',
      answerTypes: ['single-choice', 'multiple-choice', 'numeric'],
      context: (state) => '<p>HTML string</p>',
      highlightMetrics: ['key1', 'key2'],

      // For single-choice
      generateOptions: (state) => [
        { label, sublabel, consequence: (state) => ({ score, narrative, detail, metricUpdates }) }
      ],

      // For multiple-choice
      generateMultiOptions: (state) => [{ id, label, sublabel, correct, poor? }],
      evaluateSelection: (selected, state, allOptions) => ({ score, narrative, detail, metricUpdates, selectionBreakdown }),

      // For numeric
      numericConfig: (state) => ({ label, unit, min, step, hint, evaluate: (value, state) => ({ score, narrative, detail, metricUpdates }) }),

      // Show-work (works for all answer types)
      showWork: (answer, answerType, state) => [{ label, formula, values, result, highlight? }],

      nextStage: 'stage-id' | (state) => 'stage-id' | null,
    }

### 5.5 evaluateSelection Signature — Always Use Third Arg

    evaluateSelection: (selected, state, allOptions) => {
      const ids = selected.map(o => o.id);   // always extract first
      const breakdown = allOptions.map(o => ({
        label: o.label,
        selected: ids.includes(o.id),
        correct: o.correct,
        reason: /* per-option string */,
      }));
      return { score, narrative, detail, metricUpdates, selectionBreakdown: breakdown };
    }

The third arg gives access to all options — required for accurate breakdown labels. Without it, labels render as `undefined`.

### 5.6 Wiring a Simulation Into Its Apply Page

    import { ScenarioEngine } from '/js/engine/scenario-engine.js';
    import { mySim } from '/js/engine/scenarios/my-sim.js';

    let simEngine = null;

    // Inside initDepthToggle(), when depth === 'simulation' and simEngine === null:
    simEngine = new ScenarioEngine();
    simEngine.init(mySim, document.getElementById('depth-simulation-container'));

### 5.7 Test Suite

    node tests/test-runner.js js/engine/scenarios/breakeven-sim.js

Tests run:

1. **Structure validation** — required fields, answer types, option shapes
2. **Path walkthrough** — walks every possible decision path, validates consequence shapes
3. **Randomizer stress** — runs `randomizeMetrics()` 100 times, checks sanity and achievability
4. **Score distribution** — verifies all four score levels reachable across 50 runs
5. **Selection breakdown labels** — confirms no `undefined` labels
6. **Stage graph connectivity** — validates `nextStage` references resolve to real ids

Run before any simulation commit.

### 6.4 Choice Step Type

Choice steps render radio buttons and grade by exact `correctId(data, prior)` match. The correct answer must be a **function of the randomized data**, never a static "always C" trivia answer.

If a choice step has a fixed correct answer for pedagogical reasons (e.g. "book value IS the sunk cost"), opt into `intentionalSingleAnswer: true` to suppress the validator's coverage warning. This signals the test "yes, this is by design." Three Ch. 12 steps use this flag; Make-or-Buy deliberately doesn't (it should split both directions, and currently does).

### 6.5 Scenario Pool Helpers

    import { randomCompany, randomProduct } from './scenario-pools.js';

    const company = randomCompany({ category: 'manufacturing' });
    // returns { name, base, industry, suffix, category }
    //   name: full string for prose ("Bayport Manufacturing, LLC")
    //   base: standalone for possessives in show-work ("Bayport's CM")

    const product = randomProduct({ category: 'manufacturing' });
    // returns { singular, plural, category }

**Rules:**

- Call these inside `randomize()`, store the whole record on `data`
- Never call them inside `scenario()` or `showWork()` — those must read from `data`
- Categories: `manufacturing`, `process`, `service`, `retail`, `distribution`, `technology`, `healthcare`, `hospitality`, `construction`, `any`

### 6.6 Tolerance System

Numeric steps grade via tolerance. Defaults by `resultType`:

| resultType     | Default tolerance                      |
| -------------- | -------------------------------------- |
| `money-small`  | ±$1 absolute                           |
| `money-medium` | ±1% relative                           |
| `money-large`  | ±0.5% relative                         |
| `units`        | ±1 absolute (under 1,000), else ±0.5%  |
| `percent`      | ±0.5 percentage points                 |
| `years`        | ±0.1 years                             |

Override per-step with `tolerance: { value, type: 'absolute' | 'percent' }`.

### 6.7 Validator

Run before any Practice commit:

    npm run validate -- js/practice/chXX-problems.js   # single file
    npm run validate:all                                 # all chapters (skips empty stubs)

Validator runs 10 checks per problem (see SPEC.md §12 and `tests/validate-problem.js` for the full list). Key behaviors:

- Numeric steps require `unit`; choice steps don't
- Choice steps default to a coverage warning when only 1 of N options is ever correct across 50 runs — opt out per step with `intentionalSingleAnswer: true`
- Empty stub files in `js/practice/ch*-problems.js` are skipped by `validate:all`, not failed

### 6.9 Authoring Checklist — New Chapter Problem File

1. Write `js/practice/chXX-problems.js` following the schema in §6.3 (use Ch. 7 or Ch. 12 as a reference for scenario + choice patterns)
2. Use `randomCompany()` / `randomProduct()` for narrative wrappers
3. For variance-style problems, pair each numeric magnitude with a choice step for direction (fav/unfav)
4. For decision problems, end with a choice step whose `correctId` reads from `prior`
5. Add `intentionalSingleAnswer: true` only to pedagogically-fixed choices
6. Run `npm run validate -- js/practice/chXX-problems.js` — must show 0 failures
7. Write `pages/practice/chXX.html` (clone an existing picker page, swap title/description/script src)
8. Write `js/practice/chXX.js` (clone an existing picker wiring, swap import + array name)
9. Activate the tile in `js/practice/index.js` (set `available: true`, `problemCount`, `estimatedMinutes`, `href`)
10. Hard-refresh, manual browser test each problem twice — once correct, once with distractors
11. Commit message format: `feat: Practice Ch. XX — Topic (N problems)` with detail bullets

### 6.10 Anti-Patterns Specific to Practice

- **Hardcoded paths in `reviewChapters`** — always use `${BASE}pages/learn/chXX.html`, never `/pages/learn/chXX.html`
- **Hex colors in show-work** — use only the CSS custom property tokens; the show-work component handles styling
- **`Math.random()` inside `solve()` or `correctId()`** — all randomness must live in `randomize()`; solvers must be deterministic given the same data
- **Mutating `data` or `prior` inside `solve()`** — both are immutable; never modify them
- **Static answers in choice steps** — `correctId` must be a function of data, not a constant (unless `intentionalSingleAnswer: true`)
- **Calling pool helpers in `scenario()` or `showWork()`** — would re-randomize per render; pool helpers belong only in `randomize()`
- **Missing `unit` field on numeric steps** — required even if cosmetic; the engine renders it next to the input

## 12. Quick Reference — When You Add Something New

**Adding a new Learn chapter HTML page:**
1. Use `%BASE_URL%pages/...` for any internal `<a href>`
2. Include the boilerplate inline script in `<head>` (see §4.3)
3. Run `npm run build` and inspect `dist/pages/learn/chXX.html` — confirm no bare `/pages/...` paths
4. Add corresponding JS file to `js/learn/`
5. Vite auto-discovers — no `vite.config.js` change needed

**Adding a new component that renders links in JS:**
1. Declare `const BASE = import.meta.env.BASE_URL;` at top of file
2. Use template literals: `\`<a href="${BASE}pages/...">\``
3. Audit with: `grep -n '"/pages/' js/your/file.js` — should be empty

**Adding a new simulation:**
1. Create `js/engine/scenarios/<name>-sim.js` following schema in §5.3–5.4
2. All `reviewChapters` hrefs MUST use `import.meta.env.BASE_URL + 'pages/learn/chXX.html'`
3. Run `node tests/test-runner.js js/engine/scenarios/<name>-sim.js` — must pass all 6 tests
4. Wire into the Apply page per §5.6
5. Update README simulation status table

**Adding a new Practice chapter (Phase 6 workflow):**
1. Read `js/practice/SPEC.md` (Pass 2) before writing anything
2. Author `js/practice/chXX-problems.js` per §6.3 — use `ch07-problems.js` or `ch12-problems.js` as reference
3. Run `npm run validate -- js/practice/chXX-problems.js` — 0 failures required
4. Clone `pages/practice/ch22.html` → `chXX.html` (swap title, description, script src)
5. Clone `js/practice/ch22.js` → `chXX.js` (swap import + problems array name)
6. Activate the tile in `js/practice/index.js` (`available: true`, `problemCount`, `estimatedMinutes`, `href`)
7. Hard-refresh, manually test every problem twice (correct path, distractor path)
8. Commit: `feat: Practice Ch. XX — Topic (N problems)`
9. Update the README status table for Practice
